# 概要审核状态流转设计

日期：2026-10-05。状态：详细设计，未实现生产功能。依据为本目录 `README.md`、既有《爱聊文档维护约定》及第13篇的15张逻辑表。本文件只展开管理员侧“预学习→概要审核→待审子专家入口”，不增加 Agent、服务或表，不包含最终用户执行、真实数据库部署或数据迁移。

## 1. 三类状态及三个位置

不能用一个“完成”同时表达生成结束、审核通过和团队完成。

| 维度 | 保存位置 | 状态与含义 |
| --- | --- | --- |
| 构建运行 | `ep_build.status` | `active` 可执行当前阶段，包含等待管理员或处理失败；`paused` 主动暂停；`cancelled` 本次构建取消；`completed` 团队整体通过，本轮不可到达；失败另由任务和生成状态表达 |
| 生产阶段 | `ep_build.phase` | 统一阶段为 `prelearning / summary / specialists / fallback / router / production_config / final_review`；本轮只执行前两阶段并停在 `specialists` 入口，不代表已生成或审核子专家 |
| 机器生成 | `ep_artifact_revision.generation_status`、`ep_job.status` | `queued / running / succeeded / failed / cancelled`；前者描述该稿生成，后者描述执行任务，不代替人工意见 |
| 人工审核 | `ep_artifact_revision.review_status` | `pending` 尚未通过；`needs_reason` 已否决、待原因；`changes_requested` 已有明确修改依据；`completed` 管理员对该稿必要范围明确通过 |

`ep_artifact.dependency_state` 统一为 `current/stale`；`ep_clarification.status` 统一为 `open/resolved`。本轮不新增构建失败状态，页面从任务错误显示失败步骤。

生成中的修订也从开始入库，审核状态为 `pending`，页面显示“生成中，暂不可确认”，不能把所有 `pending` 都显示成可审核。可确认须同时满足：机器成功、正文及来源完整、已封存、完整内容已展示、当前版本有效、必要澄清已解决。

与 SQL 保持一致：非 `pending` 审核状态要求该稿已封存。因此只有封存旧稿可设 `changes_requested`；生成中的未封存稿被新稿替代时，仅将生成状态设为 `cancelled`，审核仍为 `pending`。

- **生产待办**：`phase + current_artifact_id` 指向当前要推进的成果；其 `current_revision_id` 是当前有效修订。
- **聊天焦点**：`focus_revision_id` 指向正在讨论或回看的修订。看旧稿、原文或聊其他问题不移动生产待办。
- **待答问题**：`waiting_question_message_id` 关联当前问题；具体未决事项保存在 `ep_clarification`。回答一次解释性问题不能自动消除其他待办。

文中的状态值是本轮协议设计；数据库、接口和原型需按同一语义对齐。`specialists` 只展示下一步入口，本轮保持 `build.status=active`，不得设置 `team.completed_build_id`，也不得创建假专家充当生成结果。

## 2. 每轮消息和角色责任

先保存管理员原话及客户端请求身份，再装配生产阶段、当前修订、展示记录、聊天焦点、待答问题、未决澄清和相关历史。历史可压缩，但不能只靠固定最近十条消息恢复审核事实。

| 环节 | 具体责任 | 不得承担的责任 |
| --- | --- | --- |
| 意图识别 | 识别询问、查看、修改、通过、否决、补原因、切换、暂停、恢复、取消；提取对象、范围、条件、多动作及歧义 | 不直接通过审核；不将引用或资料里的“通过”当成管理员命令 |
| 问题改写 | 根据可核对的上下文补指代；分别形成检索问题或修改任务；保留原话、否定、条件、范围和补全依据 | 不把“修改后可以”变成当前批准，不猜测缺失的否决原因 |
| 构建 Master | 展示完整概要和来源，回答解释，追问原因，核对原文冲突，提出修订任务，展示差异与完整新稿 | 不自行填写管理员意见，不用口头“完成”替代持久状态，不把构建角色混同运行期团队路由专家 |
| 程序与数据库 | 校验身份、阶段、目标、版本、展示证据、范围、澄清和幂等；原子保存业务操作、审核、状态、事件；控制任务接管与恢复 | 不凭模型输出的 `approved=true` 放行；不在数据库事务内等待模型或管理员 |

识别与改写可以由同一次结构化模型调用完成，无需新增 Agent。建议结果含意图、目标修订、范围、原话证据、条件、规范化内容、补全依据和未决歧义；保存在 `ep_message.interpretation`。模型给出建议，程序执行允许的操作。明确自然语言确认且证据完整时可直接确认，不强制再次点击。

## 3. 正常流转

下表“数据库记录”均指既有15表；所有业务变更追加 `ep_event`，原始消息、处理结果及 Master 回复保存在 `ep_message`。长时间生成发生在事务之外。

| 阶段 | 触发 | 前置校验 | 数据库记录 | 下一状态 | 管理员可见结果 |
| --- | --- | --- | --- | --- | --- |
| 开始预学习 | 管理员启动构建 | 有权限；所选资料解析可用；每份资料仅绑定一个明确版本；请求未执行 | 创建 `ep_build`、`ep_build_document`、初始概要空草稿及当前指针、学习成果草稿和 `ep_job`；输入版本从开始固定 | 构建 `active/prelearning`；草稿 `queued/pending` | 已开始、所选资料版本和已保存进度 |
| 预学习执行 | 工作者领取任务并逐项产出 | 租约有效；构建未暂停取消；资料版本匹配 | 更新任务检查点；保存完整学习单元、`ep_revision_source` 及依赖；保留覆盖缺口和 OCR 疑点 | 生成 `running`；人工仍 `pending` | 哪些单元已保存、哪些仍在处理；未宣称整书已理解正确 |
| 生成概要 | 必要学习输出就绪 | 来源可追溯；缺口已显式记录；无阻断生成的问题 | 为初始 `book_summary` 空草稿建立生成任务，保存依据的学习修订和来源，不重复创建初稿身份 | 构建进入 `summary`；概要 `queued→running/pending` | 概要生成中，尚不可确认 |
| 完成并展示 | 概要生成返回且通过结构和来源校验 | 目标、当前指针、租约代次及依赖有效；未暂停取消 | 保存完整 `body`、来源、内容 hash 和 `sealed_at`；标生成成功；保存完整展示消息及其版本/hash/范围 | `succeeded/pending`；待答问题为该稿审核 | 整本书概要、结构、适用限制、来源和疑点；等待人工审阅 |
| 明确通过 | 管理员批准当前完整概要 | 满足第5节全部确认条件；未决必要澄清为零 | 插入 `ep_review`；更新该修订审核状态、构建阶段及消息结果；清除本次已解决的待答问题；`current_artifact_id` 置空，聊天焦点可保留概要 | 概要 `completed`；构建 `active/specialists` | 概要已确认；停在待审子专家入口，后续阶段未实现 |
| 否决且无原因 | “不通过”等明确拒绝 | 对象为当前已展示概要；不是引用或假设 | 审核记录 `decision=reject, reason=null`；审核设 `needs_reason`；创建原因澄清和追问消息 | `succeeded/needs_reason`；生产位置不动 | 已记录否决，请说明哪里不准确、遗漏或不适用 |
| 否决且有原因 | “不通过，因为……”等明确否决 | 原话确实否决；对象、范围清楚；原文纠错与自定义规则可区分 | 写 `decision=reject` 及原因，再同事务建立新修订及生成任务；旧稿设 `changes_requested` | 旧稿已否决；新稿 `queued/pending`，成为当前待生成修订 | 否决与原因已保存，正在据此改稿；旧稿仍可查看 |
| 明确修改 | “补充适用边界”等修改要求，未表达否决 | 对象、范围及要求清楚；原文纠错与自定义规则可区分 | 保存 `ep_message.interpretation` 和新稿 `change_reason`；不写 `reject` 审核记录；旧稿可设 `changes_requested`，同事务建立新修订及任务 | 新稿 `queued/pending`，成为当前待生成修订；旧稿保留历史 | 修改要求已保存，正在改稿；不显示“管理员已否决” |
| 补充原因 | 回答待补原因问题 | 存在相符的未决澄清及先前真实否决；回答确实解释原因；版本仍有效 | 原无原因 `reject` 记录保持不变；以当前补原因消息追加带真实原因的 `reject` 审核记录，按 `message_id/action_no` 防重；同时解决澄清，保存回复关联及新稿 `change_reason`，创建新稿/任务并关联 `resolution_revision_id` | 旧稿 `changes_requested`；新稿 `queued/pending` | 原否决和补充依据均可追溯，等待新稿 |
| 展示修订稿 | 改稿完成 | 与首次生成相同校验；修改范围和来源未越界 | 封存新稿，保存完整展示消息、变更清单及原因关联；旧正文和审核历史保留 | 新稿 `succeeded/pending` | 同时显示“改了什么”和完整新稿；必须重新确认 |

原因回答解决“缺少原因”这项澄清，不代表其要求已被正确实现；正确性由新稿审阅判断。仍影响新稿的其他澄清逐项保留或重新关联，不因产生新版本而全部清空。生成结果若仍有语义疑问，Master 提问并保存澄清，不能绕过问题送入已完成状态。

`changes_requested` 只表示该稿需要修改，不是 `reject` 的替代证据。直接否决必须有管理员原话依据；补原因时追加的带原因 `reject` 记录是为既有真实否决补充依据，须关联原否决、当前补原因消息及澄清，不是凭补原因发明新的否决意图。原无原因审核记录不可覆写。条件认可、修改建议和明确修改请求均不能凭生成了新稿而反推否决。

## 4. 对话、冲突与恢复流转

| 阶段 | 触发 | 前置校验 | 数据库记录 | 下一状态 | 管理员可见结果 |
| --- | --- | --- | --- | --- | --- |
| 任一可查看阶段 | 解释、查来源、离题闲聊 | 查看权限；引用对象明确 | 保存原话、解释和必要焦点；保留原生产位置及未决澄清 | 审核不变 | 正常回答；仍能看到原待办 |
| 解释之后 | “可以”“好的” | 判断其回答的是解释、修改建议还是完整概要审核；证据不足不执行确认 | 保存识别结果及必要追问 | 审核不变，或在明确满足确认条件时执行正常确认 | 不把对解释的认可当作概要通过 |
| 条件认可 | “补上边界后就可以” | 保留条件；确认修改对象；若内容不足先澄清 | 保存条件和修改依据；条件明确时创建新稿任务，不能写批准记录 | 新稿 `pending` | 展示修改后的完整版本，请管理员再次审阅 |
| 来源冲突 | 管理员意见与书中内容不同 | 核对原文，询问是在纠正理解还是加自定义规则 | 保存原文关联、冲突说明及澄清；明确后保存修改依据；自定义学习成果标 `origin=admin_custom` | 澄清未解决前不通过；解决后走修订 | 区分书中观点与管理员意见，不改写 `ep_source_chunk` |
| 回看历史 | 切换到旧版或原文；随后说“继续” | 区分聊天焦点与生产待办；“继续”不能被推断为批准 | 只更新焦点或恢复当前待办展示；保留待补原因等问题 | 生产阶段不变 | 先前待审版本及未决问题恢复；历史稿只读 |
| 重复提交 | 网络重试、同一消息再次发送 | 相同 `client_request_id` 的请求内容与上下文必须一致 | 唯一约束定位原 `ep_message`；返回已有结果或处理中状态，不重复审核/建任务 | 原状态 | 原结果；同一身份换内容则返回幂等冲突 |
| 多标签页冲突 | 确认/修改旧版本，或并发推进 | 锁构建行后检查预期修订及 `lock_version`；核对展示 hash | 保留消息和冲突结果；不写成功审核，不把旧批准套给新稿 | 当前合法状态不变 | 指出提交版本与当前版本，展示当前稿供重新判断 |
| 修改生成中 | 新的明确修改要求 | 相对哪版、修改范围和依赖清楚；否则先澄清 | 撤销旧任务提交资格；旧未封存稿生成设 `cancelled`，审核仍 `pending`；保留旧输入，新建目标修订及任务并更新当前指针 | 新目标 `queued/pending` | 已切换到新修改要求，旧结果不能覆盖；未送审旧稿不制造人工否决状态 |
| 主动暂停 | 明确“暂停构建” | 构建非取消/完成；控制请求版本有效 | 同一短事务设构建 `paused`，保存阶段、待办和检查点；相关旧生成任务 `cancel_requested=true`、`status=cancelled`、`lease_epoch` 加1、`lease_owner/lease_until=NULL`；未完成生成标 `cancelled`，成功稿保持 | 暂停；审核原样保留 | 生成及审核推进暂停；中断原因显示“暂停”，不显示管理员否决；恢复不必等待旧外调返回 |
| 恢复 | 对暂停任务明确恢复 | 当前阶段及目标仍有效；读取已保存检查点 | 构建设 `active`；用恢复消息派生新 `dedup_key`，创建新任务身份，续接未封存目标及有效检查点；旧任务及取消标记保留，成功稿不重复生成 | 回到保存阶段；未完成稿 `queued/pending` | 从可恢复步骤继续，或继续等待原稿审阅；旧任务仍可追溯 |
| 取消 | 明确取消本次构建 | 校验构建身份与版本 | 同一短事务设构建 `cancelled`，相关生成任务置 `cancel_requested=true/status=cancelled`、递增 epoch 并清除租约；未完成生成标 `cancelled`，成功稿不变；保留草稿、消息、审核和事件 | 终止本次构建 | 已取消，保留历史；不能通过普通“继续”复活，重新开始另建构建版本 |
| 生成失败 | 模型、工具或生成步骤出错 | 确认失败属于当前有效任务 | 保存 `ep_job.error/checkpoint`，该未完成稿生成设 `failed`；构建保持 `active`，阶段不动，失败由任务和生成状态表达 | 人工审核不变 | 失败步骤、已保存进度、可重试；不记录否决 |
| 重试失败步骤 | 管理员明确继续或重试 | 未暂停取消；输入版本及依赖有效；未封存目标可继续 | 用重试消息派生新 `dedup_key`，创建新任务身份并引用旧任务的有效检查点/输入；保留旧任务、错误和事件；新任务领取时递增自身 attempt/lease epoch | 构建 `active`，生成 `queued→running` | 从最后成功检查点续作；新依赖要求改稿则另建修订，不重复创建已有成果 |
| 单条消息失败 | 识别、解释或保存操作失败 | 检查该消息是否已有成功业务提交 | 已入库消息保存终结的失败结果；业务事务失败则全部回滚；未入库或结果未知请求以原身份查询/重送；明确重试已失败消息须新 `clientRequestId` 和任务身份 | 既有审核及构建阶段不变 | 同键重放返回已保存结果；新请求才发起再次处理，不静默重复副作用 |
| 迟到生成结果 | 旧工作者返回，或暂停取消后返回 | 必须核对当前目标、任务状态、租约 owner/epoch、有效期、取消标记及依赖 | 校验失败不挂接正文、不更新当前指针，不产生成功审核；记录可追溯的丢弃结果事件 | 当前状态不变 | 保持当前版本；不得突然跳回旧稿 |
| 刷新/换节点 | 重连页面或进程恢复 | 权限和构建身份；以数据库提交状态为准 | 读取构建、当前/焦点修订、消息、审核、澄清和任务；按事件序号补读 | 恢复最后已提交状态 | 对话、版本、待答问题、修改进度和审核状态恢复 |

暂停不同于插话：插话不取消生成。暂停状态仅允许查看、解释和控制操作；修改/确认请求保留原话并告知需恢复，不自动排队执行。暂停时撤销提交资格不保证供应商立即停算或不收费；恢复依检查点和已保存外部任务标识处理，不能盲目重复外调。

生成任务要求构建 `active`；`interpret_message` 在 `paused/cancelled` 仍可领取，但落地动作须重检阶段权限。暂停可处理恢复；取消仅保留只读查看和解释，不允许恢复构建、生成或审核。

恢复/重试一律新建任务身份，旧任务不清除取消标记、不恢复为 `queued`，历史错误和检查点保持可追溯；恢复任务在 `input.resumedFromJobId` 关联旧任务。新任务仅能续接仍有效的未封存修订；不能重写封存稿。暂停在同一短事务内将旧生成任务置 `cancelled`、递增 epoch 并清除租约，立即撤销提交资格；外部响应和工作者本地清理可以晚到，不能阻塞恢复，也不能将新任务接续的修订再次标为失败或取消。控制消息自身的 `interpret_message` 任务正常保存处理结果；其他消息在暂停/取消后只能执行查看、解释及合法控制，不能因此恢复生成或审核。非终结任务的失租接管仍是同一任务内递增租约代次，与管理员对已暂停/失败工作的恢复重试不同。

## 5. 确认和修订的程序约束

一次成功的完整概要确认须同时校验：

1. 操作者具备该构建的审核权限，原始消息确实表达批准，且没有未满足条件；引用文本不能作为授权。
2. 构建运行、处于概要审核阶段；当前成果类型为 `book_summary`，提交目标与当前修订一致。
3. 当前稿生成成功且已封存；内容、来源依赖和 hash 相符，无过期依赖或阻断审核的未决澄清。
4. 服务端展示消息关联该对象、修订、hash 和范围；客户端确认上下文指向已实际呈现的完整稿。仅排队发出消息不算已展示，也不能证明管理员已经阅读理解。
5. 确认范围为 `summary.full`，审核决定值统一为 `approve/reject`。仅认可标题、某一句或修改方向不能将整份概要标为 `completed`。

完整展示消息在 `context_snapshot` 保存对象、版本、hash、范围及完整内容引用；管理员回复携带对应展示消息身份。刷新可以重新呈现同一封存稿，不需要生成新修订。旧稿即使当时展示过，也不能批准为当前稿。

业务事务顺序：锁 `ep_build` → 检查幂等与预期版本 → 检查上述条件 → 写 `ep_review`、审核状态、阶段、消息结果与 `ep_event` → 提交。消息接收事务可以更早提交以保留原话，业务成功结果必须与业务变更一起提交。消息/事件序号在同一构建行锁内分配；所有入口采用一致锁顺序。

改稿先在短事务内保存原因、旧稿审核状态、新稿身份与任务输入，再进行模型调用。新稿未封存时可保存部分结果；送审后禁止覆写正文、提示词、来源集合和 hash。hash 覆盖规范化完整审阅内容及所引用来源/依赖身份，具体序列化约定由接口合同固定；不能只散列页面摘要。旧确认永不自动继承；修改只将受影响的当前下游成果标为 `dependency_state=stale`，不改无关成果，也不删除历史审批。

同一消息中的多个动作使用 `message_id + action_no` 防重；存在歧义或依赖尚未完成时不执行相关副作用。“先修改再批准”只可创建修改任务，不可预先批准未展示结果。回复模型建议“已完成”时，页面仍以数据库状态为准。

## 6. 持久化与边界

数据库是权威来源：`ep_message` 保存原话/展示/解释/结果，`ep_review` 保存版本化人工决定，`ep_clarification` 保存逐项未决问题，`ep_job` 保存执行及检查点，`ep_event` 保存可补读事件。只有概要完整批准才推进到子专家入口，后续职责、模型、工具、特色能力、完整提示词、边界的审阅均尚未实现。

Redis 仅辅助不可变内容缓存、通知和共享限流。丢失通知后用 `ep_event` 补读，重复事件按构建内序号去重；按接口合同使用同一次只读 REPEATABLE READ 事务读取快照和 `lastEventSeq`，随后补读事件，不能分开查询游标与状态。Redis 不可用不丢审批；数据库不可用时不能宣称写入成功。外部模型可能重复计费，设计只保证有效业务结果不重复提交。

原型可以用演示数据及 localStorage 展示有限交互；这不验证数据库事务、集群接管、模型语义能力或服务端展示校验。原型若只接受有限句式或使用演示 hash，应显式标识，不将该限制写成生产要求。真实资料、密钥和既有运行状态均不在此次设计验证范围。

## 7. 验收用例

以下是设计要求及后续验收条件，不表示已经运行生产测试。

| 场景 | 必须观察到的结果 |
| --- | --- |
| 生成途中查看记录、刷新 | 已有任务及部分草稿；显示生成中且不可确认，恢复已保存进度 |
| 生成完成 | `succeeded/pending`；完整正文、来源、限制及展示版本可见，未写批准 |
| 当前完整概要明确通过 | 仅该修订 `completed`，阶段为 `specialists`；无真实子专家、无团队完成指针 |
| 不通过但未说原因，随后闲聊再继续 | 原否决与 `needs_reason` 保留；继续时追问仍未解决的原因 |
| 补充有效原因 | 原无原因 reject 不变；当前消息追加带原因 reject 并解决澄清，同消息重放不重复追加；记录关联既有否决，不能伪造新否决意图；先保存依据再调模型，新稿重新待审 |
| “改好后就可以” | 没有批准记录；展示完整新稿和差异后仍需明确确认 |
| “补充适用边界”，未表达否决 | 修改依据进入 `interpretation/change_reason`，旧稿可为 `changes_requested`；不新增 `reject`，页面不显示已否决 |
| 解释之后说“可以”、仅认可标题、引用中含“通过” | 不把这些表达自动当作完整概要确认；歧义时只澄清必要对象/范围 |
| 自定义意见与原文冲突 | 展示来源并区分纠错/自定义规则；原文不被改写，不捏造来源 |
| 同一请求重放、同身份更换内容 | 前者返回原结果且无重复任务/审核；后者幂等冲突 |
| 两标签页分别修改与批准旧稿 | 构建锁下只有合法顺序生效；后者冲突，无旧批准移到新稿 |
| 暂停后立即恢复，旧模型调用仍未返回；取消后说继续 | 暂停同事务旧 job cancelled、epoch 加1、清租约；无须等待旧外调结束即可创建新任务续接；旧取消标记和历史保留，迟到结果不能挂接；取消构建不复活 |
| 当前任务失败后重试；旧租约工作者恢复 | 新消息派生新任务及 dedup_key，复用有效未封存修订/检查点，旧任务保留失败；审核不被否决；旧任务/epoch 无法覆盖当前结果 |
| 审核提交失败、提交后通知丢失 | 前者没有半成功批准；后者从数据库恢复已成功批准并补读事件 |
| 切历史版、刷新、返回当前待办 | 焦点和待办独立恢复；旧稿只读，必要澄清不因切换或刷新消失 |

本文件验证范围为流程完整性、字段来源及文字一致性；集群并发、事务约束、暂停任务和展示证据均需在后续真实实现中验证。
